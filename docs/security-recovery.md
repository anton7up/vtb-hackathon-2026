# Учебное восстановление после «Это был не я»

Это сценарий прототипа, **не настоящая банковская проверка личности**. До завершения действует блокировка всех исходящих операций. Не используется обычная кнопка сотрудника «разблокировать».

1. Клиент сообщает о чужом событии из другой сессии, открытой до события. API сохраняет SHA-256 именно этой сессии в закрытом поле `securityLock.reporterSessionHash`; остальные сессии отзываются в одной транзакции с блокировкой.
2. Только эта прежняя сессия может запросить восстановление. API повторно проверяет пароль, с ограничением числа попыток. Запрос привязан к конкретной тревоге, критическому изменению и сессии. Срок — 15 минут **реального** времени, независимо от демонстрационной перемотки.
3. Сотрудник моделирует независимую проверку, заполняет три пункта и комментарий. Интерфейс прямо предупреждает, что реальный канал проверки личности не реализован. Разрешение сотрудника **не снимает блокировку**.
4. Клиент в той же прежней сессии отдельно подтверждает завершение, снова вводит текущий пароль и задаёт новый (от 12 до 200 символов, отличается от прежнего). API атомарно меняет соль и хеш пароля, снимает только `securityLock`, отзывает **все** сессии владельца, возвращает принудительный выход и удаляет cookie. Требуется новый вход с новым паролем.

Сохраняются баланс, завершённая история, обращения, жалобы, реестр, действующая группа доверенных лиц, лимиты, критическое изменение и оставшаяся 24-часовая пауза. Старые незавершённые исходящие операции и разрешения отменяются; автоматического повторного списания нет. Сохраняется аудит восстановления.

Если прежняя сессия потеряна/истекла, или блокировка создана старой версией без доказательства сессии, сценарий остаётся закрытым. Нужна проверка по независимому банковскому каналу; прототип не подменяет её логином, чекбоксом сотрудника либо статическим кодом.

## Интеграция

`lib/security-recovery.mjs` — чистые переходы состояния. API отвечает за роли, CSRF, свежую проверку пароля и CAS-транзакцию с отзывом сессий. `safeSecurityLock()` и `serializeSecurityRecovery()` — единственный публичный вид: хеши и отпечатки никогда не отправляются в браузер.

Формы: `security-recovery-form` (`data-recovery-step=request|complete`, текущий пароль `security-recovery-password`; только для завершения — `security-recovery-new-password` и повтор `security-recovery-repeat-password`), `security-recovery-review-form` (три checkbox `knownChannel`, `incidentReviewed`, `accessSecured`; textarea `security-recovery-comment`; submitter `verdict=approve|reject`). Все пароли читаются обработчиком однократно и сразу очищаются; не хранятся в UI state. Повтор нового пароля проверяется интерфейсом, `newPassword` — повторно на сервере. Открытый пароль не записывается ни в `bank_state`, ни в журналы.
