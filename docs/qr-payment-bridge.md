# Учебный мост QR → получатель → реестр → перевод

## Что реализовано

Разбор QR остаётся локальным и сам не отправляет деньги. По отдельной кнопке клиент передаёт текст QR нашему серверу. Учебный адаптер по **точному совпадению** одного из двух вымышленных платёжных ID определяет канонического получателя и сумму:

| Пример | Получатель | Сумма |
| --- | --- | --- |
| `normal` | `DEMO-FAMILY-001` — Мама | 1 000 ₽ |
| `shared` | `DEMO-CLASS-NORMAL` — Тест · Нормальный перевод | 3 000 ₽ |

Второй получатель совпадает с вымышленной исторической операцией, по которой можно подать жалобу. Учебный реестр общий: решение сотрудника по обращению влияет на следующую попытку перевода, в том числе другого клиента. Сам черновик, отправка жалобы или ответ ИИ отметку риска не устанавливают.

Это не интеграция СБП/НСПК, не подтверждение существования ссылки и не проверка подлинности наклейки. Изображение QR не содержит надёжного знания, какому магазину клиент собирался платить.

## Контракт сервера

`POST /api/qr/resolve` с `{ payload }` вызывает `resolveQrPayment(payload, registry, { reviewedComplaintCount })`. Возвращаются только учебный источник, канонический получатель, сумма, статус реестра и необязательное обезличенное число рассмотренных жалоб. Причины, тексты жалоб, идентификаторы обращений и другие клиенты не раскрываются.

Статусы реестра: `clear`, `watch`, `blocked`, `unavailable`. Отсутствие отметок не равно безопасности и не разрешает операцию.

Перевод проходит через обычный `/api/action` (`attempt`, затем отдельный `confirm`) с `qrPayload`, `qrFixtureId` и `requestId`. На **каждом** этапе `qrTransferRequest` заново сопоставляет точный текст и ID примера. Получатель, сумма и тип операции берутся только из серверного справочника, а не из полей запроса или клиентского разбора QR. Дальше действуют существующие проверки счёта, реестра, классификатора, повторного подтверждения и идемпотентности. `watch` передаёт перевод на рассмотрение, `active` блокирует его.

В операции можно хранить только `paymentContext`: источник, версия адаптера, ID примера и канонический получатель. Исходный текст QR и платёжные URL не нужны в банковской истории.

## Границы

- Неизвестные реальные СБП ID, подписки, чеки, обычные URL и произвольные реквизиты не оплачиваются этим адаптером.
- Добавление параметра суммы, смена регистра, пробелы, другой ID или подмена домена не расширяют разрешённые варианты.
- Никакие ссылки из QR не открываются и внешняя сеть не используется.
- Ответ адаптера не является разрешением операции; реестр повторно проверяется перед подтверждением.
- Пользователь явно подтверждает учебное списание. При ошибке или недоступности продолжение не предлагается.
- Обычный вариант получателя может получить отметку позже: учебный пример не обходит актуальный реестр.

## Проверка для жюри

1. Открыть QR-примеры и выбрать «Обычный учебный QR». Разобрать, затем отдельно проверить получателя в учебном банке. Просмотр не меняет баланс; существующие отметки и ограничения сохраняют приоритет.
2. Выбрать «Жалоба защищает следующего клиента». Сумма и получатель появятся только из адаптера, не из имени QR.
3. Подать жалобу из истории первого клиента и передать её сотруднику. До решения сотрудника отметки нет.
4. Сотрудник назначает дополнительную проверку или стоп-лист.
5. Второй клиент повторно проверяет тот же QR: видит только отметку/обезличенное число жалоб. Попытка перевода получает обычное серверное решение без списания при проверке/блокировке.
6. Изменить один символ QR или выбрать подписку: получатель не определяется, оплата через прототип недоступна.

QR PNG воспроизводимы командой `node scripts/generate-qr-demos.mjs`; генератор проверяет обратное распознавание всех текстов до записи файлов.
