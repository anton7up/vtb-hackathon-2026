# Связанная проверка покупки

Клиент добровольно указывает сайт, получателя, сумму и короткое объяснение. Банк **не получает URL магазина из обычного перевода автоматически**. Связь сайта с получателем — заявление клиента, а не установленный факт.

Сервер проверяет ввод через `preparePurchaseInput(body, RECIPIENTS)`. Сумма — целое число копеек. Требуется явное согласие. Полный URL существует только в памяти запроса. Сетевой анализ выполняет исключительно существующий защищённый `runtime.inspectWebsite({url, demoScenario})`; модуль не имеет собственного fetch и не ослабляет SSRF-защиту. Дополнительно можно вызвать `runtime.cbrWarning.checkUrl(url)`. Реестр получателей берётся из банковской БД, не из запроса клиента.

`createPurchaseCheck(input, {scan, cbr, registry, model, actualNow})` сохраняет только origin/hostname, редактированное объяснение, разрешённые статические описания признаков, статусы источников и привязку к сумме/получателю. `model` — серверный результат `checkPhishingUrl`: сохраняется только класс URL-модели, без подачи её score как вероятности мошенничества покупки. Не сохраняются HTML, путь, query, fragment, заголовок страницы, содержимое форм, редиректы и произвольные сообщения сканера. Скрытие персональных данных в свободном тексте — best effort, а не обещание анонимности. Qwen автоматически не вызывается.

`putPurchaseCheck(state, report)` сохраняет последние 30 кратких отчётов. Доступ к ним имеет владелец и сотрудник при выборе этого клиента; они не попадают в общий реестр. `purchaseCheckId` в операции ссылается только на отчёт из серверного состояния владельца. При подтверждении повторно сверяются тип операции, получатель, сумма и срок — 15 минут **реального времени**, независимо от учебной перемотки.

`purchaseGate(state, request, actualNow)` возвращает:

- `null` — нет привязанной проверки или конкретных сигналов в завершённой проверке не найдено. Это не разрешение списания и не гарантия магазина.
- `PURCHASE_REVIEW` — есть признаки риска HTML, запись ЦБ или отметка реестра. Требуется сотрудник; это не автоматическое обвинение магазина.
- `PURCHASE_CHECK_INCOMPLETE` — часть проверок недоступна. Такой результат не считается безопасным; возможна отдельная проверка сотрудником.
- `PURCHASE_INVALID` / `PURCHASE_EXPIRED` — чужой/отсутствующий отчёт, другая сумма/получатель, некорректный срок. Следует создать новую проверку; одобрение сотрудника не должно обходить эти ошибки привязки.

Интеграция преобразует первые два сигнала проверки в policy-класс `review`, не заменяя `block` или недоступность основной модели. Сотрудник разрешает только отдельное подтверждение сохранённой операции. Финальные проверки стоп-листа, паузы, баланса и доверенных лиц остаются обязательными. Само завершение проверки и кнопка «Продолжить» никогда не списывают деньги.

Для жюри допускаются четыре точных `demoScenario` существующего сканера: `brand_clone`, `shop_clone`, `ordinary_shop`, `challenge`. Их URL принудительно берётся из allowlist, источник отчёта явно отмечен «Учебный HTML». Они не имитируют успешную загрузку реального магазина.

UI-контракт: `renderPurchaseCheck(ui,state,helpers)` с полями `purchaseUrl`, `purchaseRecipient`, `purchaseAmount` (рубли строкой), `purchaseExplanation`, `purchaseConsent`, `purchaseBusy`, `purchaseError`. Submit формы `#purchase-check-form`; выбор отчёта — `[data-purchase-use]`. `renderPurchaseCase(op,state,helpers)` показывает ту же сводку владельцу или сотруднику без отправки банковских данных внешнему ИИ.
