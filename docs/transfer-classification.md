# Контракт классификации переводов

## Три результата

Модель возвращает JSON с обязательными полями:

```json
{
  "class": "review",
  "model_version": "model-v1"
}
```

Допустимы только строковые классы:

| class | Название | Действие сайта |
|---|---|---|
| normal | Нормальный | После проверки остальных правил клиент может подтвердить перевод. Сам ответ модели не списывает деньги. |
| review | Нужно проверить | Создаётся операция pending без списания. Сотрудник отдельно разрешает подтверждение или отклоняет перевод с комментарием. |
| block | Блокировка | Создаётся остановленная операция без списания. Сотрудник не может разрешить её через очередь review. |

Это оценка и мера защиты, а не доказательство совершения мошенничества.

## Приоритет правил

1. Авторизация, права, корректная сумма и реквизиты.
2. Блокировка «Это был не я».
3. Реестр, защитная пауза и баланс.
4. Классификация normal / review / block.
5. Явное подтверждение клиентом.

Класс normal и ручная проверка не отменяют предыдущие ограничения. Проверки повторяются непосредственно перед списанием. Ранее остановленные платежи не исполняются автоматически.

Недоступный сервис, неизвестный класс или неправильный формат — не normal и не четвёртый класс. Проверка считается незавершённой, classification=null, операция pending с кодом MODEL_UNAVAILABLE, деньги не списываются. Старая остановленная операция не отправляется при восстановлении сервиса: нужна новая проверка.

## Обученная модель и резервный демонстрационный режим

`pipeline/artifacts/fraud_model.joblib` — обученная на синтетических данных модель `HistGradientBoosting` с калибровкой. `pipeline/service.py` загружает её один раз, слушает только loopback и возвращает вероятность и решение 0/1/2. `lib/transfer-classifier.mjs` формирует вход из серверного баланса и истории, вызывает сервис и переводит решения в `normal/review/block`. Клиент не может передать свой вердикт или признаки API.

Модель включается только при `TRANSFER_MODEL_URL=http://127.0.0.1:8101/v1/classify`. Если настроенный сервис недоступен или вернул неверный ответ, классификация считается незавершённой и деньги не списываются. Автоматического отката на благоприятную заглушку нет.

Без `TRANSFER_MODEL_URL` остаётся резервная серверная заглушка для разработки и тестов. Сотрудник может выбрать её ответ в кабинете; этот режим явно помечен как не-ML.

Для проверки отказов есть режим «Сервис недоступен» — это ошибка сервиса, не дополнительный класс. По умолчанию используется normal. На экранах явно написано «Демо-заглушка · не ML».

Ответ адаптера дополнен серверными метаданными source=mock, evaluated_at и config_revision. Клиенту нельзя доверять эти поля из тела запроса.

## Признаки и аудит

Сервер формирует и сохраняет вместе с операцией:

- amount_kopecks — сумма в копейках;
- recipient_id — демонстрационный идентификатор получателя;
- is_new_recipient — не было успешного перевода до действующей защитной паузы, либо вообще до текущего момента вне паузы;
- recorded_transfers_last_hour — число записанных переводов за последний час, включая остановленные; разрешённая проверка без подтверждения отдельную запись не создаёт;
- completed_amount_last_hour_kopecks — сумма только выполненных переводов за час;
- access_changed_last_24h — критичные данные доступа менялись за последние 24 часа.

Признаки хранятся на сервере и доступны сотруднику в API, но не выдаются клиентскому кабинету. Подключённая Python-модель использует собственный контракт из 13 признаков в `pipeline/features.py`; этот краткий набор остаётся аудиторской сводкой серверного решения. Резервная заглушка признаки не использует.

## Проверка сотрудником

- review-transfer доступен только сотруднику: operationId, verdict=approve|reject, comment (от 5 символов).
- Решение фиксируется в журнале. Обычный ответ на обращение НЕ является разрешением перевода.
- approve разрешает клиенту подтвердить сохранённую операцию в течение 15 минут реального серверного времени. Списание не выполняется сотрудником.
- confirm-reviewed доступен только клиенту и использует сумму и получателя из серверной операции, а не из присланных полей.
- Разрешение одноразовое: повторный запрос возвращает уже выполненную операцию без второго списания.
- Смена критичных данных или режима заглушки делает разрешение устаревшим; при подтверждении требуется новая проверка. Новые стоп-сигналы и класс block останавливают перевод.
- Срок разрешения считается по реальному времени, а не по демонстрационной перемотке 24 часов.
- reject окончательно останавливает исходную операцию. Подмена суммы, получателя, роли или класса в запросе не даёт права списать деньги.

Классификация относится к переводам. Демонстрационное снятие наличных пока подчиняется существующим правилам паузы и блокировки аккаунта, без ML-класса.
# Быстрая проверка по получателю

В резервном режиме без Python-сервиса в списке есть три вымышленных получателя: `DEMO-CLASS-NORMAL`, `DEMO-CLASS-REVIEW`, `DEMO-CLASS-BLOCK`. Их классы фиксированы на сервере и используются только как тестовые fixtures. При подключённой обученной модели эти ID оцениваются моделью на общих основаниях; фиксированный класс не применяется. Клиентские поля `classification`/`demoClass` результат не задают.

У каждого добавлена явно помеченная вымышленная история прежнего перевода. Поэтому 24-часовая пауза не мешает проверить классы, но реестр, недостаток средств и блокировка аккаунта по-прежнему имеют приоритет. Добавление истории не списывает деньги и не меняет существующие операции. История добавляется идемпотентно и для ранее созданной демо-базы; сброс демо не нужен.

`normal` открывает отдельное подтверждение без немедленного списания; `review` автоматически открывает привязанный ИИ-диалог; `block` останавливает перевод. Настройка заглушки сотрудником продолжает действовать для остальных получателей.
