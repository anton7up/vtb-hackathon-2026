# Синтетический датасет банковских переводов

Файл: `bank_transfers.csv` · 9 038 строк · 01.01.2025 — 31.03.2025 · фрод 1,00%

Сгенерирован скриптом `make_transfers_dataset.py` (seed=42). Заменяет PaySim: меньше строк,
но больше смысла — есть баланс отправителя, реальные повторные получатели и политика решений.

## Схема

| Колонка | Тип | Смысл |
|---|---|---|
| `timestamp` | datetime | дата и время операции, `YYYY-MM-DD HH:MM:SS` |
| `sender_id` | str | отправитель, `C00001`…`C00600` (600 клиентов) |
| `sender_balance` | float | баланс отправителя **до** операции |
| `amount` | float | сумма перевода, всегда `> 0` и `<= sender_balance` |
| `receiver_id` | str | получатель: клиент `C…` или счёт дропа `C######` |
| `label` | int | **решение по политике**: 0 пропустили / 1 на проверку / 2 заблокировали |
| `is_fraud` | int | **истина**: 1 — мошенничество. Для оценки, не для обучения политики |

## Как читать `label`

`label` — это не разметка фрода, а применённое решение с шумом. В классе 0 есть и легальные
операции, и **пропущенный** фрод; в классе 2 — и фрод, и **ошибочные блокировки**.

| label | всего | из них фрод | что значит |
|---|---|---|---|
| 0 | 8 504 | 7 | пропущено: 8 497 легальных + 7 пропущенных фродов |
| 1 | 429 | 12 | отправлено оператору: 417 легальных + 12 фродов |
| 2 | 105 | 71 | заблокировано: 71 фрод + 34 ложных блокировки |

Поэтому:

* **обучать** модель лучше на `is_fraud` (бинарная вероятность), а 0/1/2 получать порогами;
* если всё же нужна трёхклассовая модель — обучайте на `label`, но помните, что она
  воспроизводит политику, а не ищет мошенничество;
* метрики качества считайте по `is_fraud`: precision/recall/PR-AUC.

## Что заложено в данные

* 600 клиентов, у каждого «круг общения» из 2–9 постоянных получателей; 85% переводов — им.
* 15% переводов — новому лицу, и они в среднем крупнее (`amount / balance` выше).
* Балансы согласованы: каждая операция уменьшает счёт отправителя и увеличивает счёт получателя.
* Легальные «трудные» случаи: перевод почти всего баланса знакомому (2% операций),
  крупные суммы новым получателям, ночные переводы.

Типологии фрода (всего 90 операций):

| Тип | Доля | Как выглядит |
|---|---|---|
| `takeover` | 37% | вывод 85–100% баланса на свежий счёт (иногда 30–60% и днём) |
| `collusion` | 21% | платёж «своему» счёту круглой суммой |
| `structuring` | 21% | дробление на 8 500–9 900 одному получателю |
| `mule` | 8% | цепочка перегонок между счетами дропов |
| `probe` | 13% | мелкий «тестовый» перевод 150–600, который политика часто пропускает |

## Признаки, которые стоит построить

```python
df = df.sort_values("timestamp")
pair = ["sender_id", "receiver_id"]

df["payee_tx_before"] = df.groupby(pair).cumcount()          # 0 = перевод первый
df["is_new_payee"] = (df["payee_tx_before"] == 0).astype(int)
df["days_since_first"] = (df["timestamp"] -
    df.groupby(pair)["timestamp"].transform("first")).dt.days
df["amount_ratio"] = df["amount"] / df["sender_balance"].clip(lower=1)
df["hour"] = df["timestamp"].dt.hour
df["night"] = ((df["hour"] < 6) | (df["hour"] >= 23)).astype(int)
df["sender_seen"] = df.groupby("sender_id").cumcount()
```

`cumcount` по отсортированным данным смотрит только в прошлое — утечки нет. Для теста
считайте частоты по train и переносите через `map(..., fillna(1))`.

## Ориентир по качеству

Временной сплит (первые 2 месяца → train, последний → test), `HistGradientBoosting`:

* PR-AUC ≈ **0,89**, ROC-AUC ≈ **0,97**;
* при пороге 0.5: 29 из 36 фродов, 3 ложных блокировки.

Это специально не идеальная задача: часть фрода выглядит обычно (мелкие «пробные» переводы,
дневные частичные выводы), а часть легальных операций похожа на фрод (вывод всего баланса
знакомому).

## Ограничения

* Данные синтетические: распределения сумм и поведения упрощены.
* 9 тыс. строк хватает для отладки пайплайна, но не для продакшн-модели (класс «блокировка»
  — 105 примеров).
* Пороги 0,2/0,5 на этих данных не настраивать: они зависят от стоимости ошибок в вашем банке.
* Персональных данных нет: только идентификаторы вида `C00001`.
