# Синтетический датасет платежей юрлиц и ИП

Файл: `legal_transfers.csv` · 40 252 строки · 01.01.2025 — 30.04.2025 · фрод 1,00% (403 строки)

Сгенерирован скриптом `make_legal_dataset.py` (seed=42). Пара к `synthetic/bank_transfers.csv`
(физлица): та же идея, но клиенты — 180 ООО и 120 ИП, а в данных есть то, что банк знает
о платеже бизнеса: ИНН и счёт получателя, назначение, канал, устройство, смена доступа.

## Схема

Одна строка = один исходящий платёж. Всё, кроме двух последних колонок, банк знает
в момент платежа — это «сырые» данные, из них `features.py` считает признаки.

| Колонка | Откуда в банке | Смысл |
|---|---|---|
| `timestamp` | платёжка | дата и время, `YYYY-MM-DD HH:MM:SS` |
| `client_id` | профиль | плательщик, `L00001`…`L00300` |
| `client_type` | профиль | `OOO` / `IP` |
| `client_balance` | профиль | остаток **до** платежа |
| `amount` | платёжка | сумма, всегда `<= client_balance` |
| `receiver_inn` | платёжка | ИНН получателя (10 цифр — юрлицо, 12 — ИП/физлицо) |
| `receiver_account` | платёжка | счёт получателя, 20 цифр: `40702…` юрлицо, `40802…` ИП, `40817…` физлицо, `03100…` казначейство |
| `receiver_type` | по счёту | `UL` / `IP` / `FL` |
| `purpose` | платёжка | `goods`, `services`, `rent`, `tax`, `salary`, `loan`, `refund`, `other` |
| `channel` | сессия | `web` / `mobile` / `1c` (выгрузка из 1С) |
| `device_id` | сессия | устройство; `D…` — клиента, `X…` — злоумышленника |
| `hours_since_access_change` | профиль | часов с последней смены телефона/пароля/пользователя; `9999` — не менялись |
| `receiver_blacklisted` | база ЦБ / стоп-лист | 1 — счёт получателя в базе |
| **`is_fraud`** | — | **ответ**: 1 — мошенничество. На нём обучаем |
| `fraud_kind` | — | тип мошенничества. **Только для анализа, в модель не подавать** |

Метки политики 0/1/2 (как `label` у физлиц) здесь нет: модель обучаем на `is_fraud`,
а 0/1/2 получаем порогами — так же, как в `pipeline/`.

Идентификаторы (`client_id`, `receiver_inn`, `receiver_account`, `device_id`) в модель
напрямую **не подаются**: из них по истории считаются признаки вроде «новый получатель»
или «знакомый ИНН, но новый счёт».

## Что заложено в «мир»

* **Клиенты.** ООО: баланс ~1,2 млн (медиана), 12–45 платежей в месяц, 2–25 сотрудников.
  ИП: баланс ~150 тыс., 3–15 платежей, 0–3 сотрудника. Балансы логнормальные.
* **Постоянные контрагенты.** Поставщики и подрядчики из общего пула 1 400 компаний
  (одни и те же поставщики у многих клиентов), аренда — одна сумма каждый месяц,
  налоги в казначейство (ООО ежемесячно, в апреле — за квартал), кредит банку.
* **Зарплата.** 5-го и 20-го, всем сотрудникам в один день. У 60% ООО — одним реестром
  через банк, у остальных — пачкой переводов физлицам.
* **ИП переводит себе на личную карту** — норма (получатель — физлицо с ИНН самого ИП).
* **Остаток** уменьшается с каждым платежом; оплаты от покупателей в выгрузку
  не входят и моделируются равномерным притоком.

### Трудные легальные случаи

Без них модель выучила бы правило «новое = фрод». Каждый похож на один из типов мошенничества:

| Случай | На что похож |
|---|---|
| Зарплата пачкой физлицам в один день | `drain` |
| 4% поставщиков сменили банк: тот же ИНН, новый счёт | `bec` |
| Крупная разовая закупка у нового поставщика (20–60% остатка) | `ceo_fraud` |
| Оплата самозанятым, иногда новым людям | `ip_social`, `drain` |
| Возвраты покупателям-физлицам | `drain` |
| ИП выводит себе 80–95% остатка | `ip_social`, `dbo_takeover` |
| Новый компьютер / бухгалтер (12% клиентов), смена телефона или пароля (~17%) | `dbo_takeover` |
| Легальный счёт по ошибке в стоп-листе | `receiver_blacklisted` |

## Типы мошенничества

| Тип | Строк | Как выглядит |
|---|---|---|
| `bec` | 96 | подмена реквизитов: **знакомый ИНН поставщика, новый счёт**, обычная сумма, рабочее время, своё устройство. Самый трудный |
| `drain` | 104 | вывод остатка пачкой: 3–8 платежей разным новым получателям (в основном физлицам) за 1–2 часа, в сумме почти весь остаток. В половине случаев — новое устройство |
| `dbo_takeover` | 90 | захват интернет-банка: смена доступа за 0–48 ч, новое устройство, канал `web`, часто вечер/ночь, 1–3 платежа новым получателям |
| `ip_social` | 61 | владельцу ИП звонит «служба безопасности»: переводы физлицу на «безопасный счёт», 50–100% остатка, своё устройство, чаще `mobile` |
| `ceo_fraud` | 52 | «директор» в мессенджере: срочная оплата новому контрагенту, 20–60% остатка, назначение `other`/`loan` |

Счета дропов общие (150 шт.), несколько «популярных» получают деньги от многих жертв —
это даёт сигнал «на счёт недавно начали платить разные клиенты». 30% дропов — в базе ЦБ.

## Сплит

Фрод есть в каждом месяце (87 / 105 / 88 / 123), поэтому сплит по времени:
**январь–март → train, апрель → test** (~120 фродов в тесте).

Не делите случайно: клиенты повторяются, и модель «узнает» клиента из будущего.

## Ориентир

Быстрая проверка `HistGradientBoosting` на грубых признаках (без «скоростных» за час/сутки):
PR-AUC ≈ 0,89 на апреле. Хуже всего ловится `bec` — его выдаёт в основном признак
«знакомый ИНН, новый счёт», который ещё нужно построить.

## Перегенерация

```powershell
py synthetic_legal/make_legal_dataset.py --fraud-share 0.01 --seed 42
```

Около 5 секунд. С тем же seed — тот же файл. Другой seed — другой датасет с теми же свойствами.

## Ограничения

* Синтетика: распределения упрощены, пороги продакшна на ней не настраивать.
* Входящих платежей нет — только исходящие.
* Персональных данных нет: ИНН и счета случайные.
