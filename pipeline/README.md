# Модель фрода по переводам

Папка готова к передаче как есть: внутри обученная модель, пороги, код расчёта
признаков и пример подключения. Переобучение не требуется — нужен только Python.

```
pipeline/
├── features.py          # 13 признаков — общий код для обучения и прода
├── policy.py            # вероятность -> решение 0/1/2
├── train_fraud.py       # обучение: CSV -> модель + отчёт
├── predict_example.py   # пример применения (то, что нужно бэкенду)
├── requirements.txt     # точные версии пакетов
├── README.md            # этот файл
└── artifacts/           # результаты обучения
    ├── fraud_model.joblib
    ├── thresholds.json
    ├── metrics.json
    ├── predictions.csv
    └── report.md
```

## Быстрый старт

```powershell
py -m pip install -r pipeline/requirements.txt
py pipeline/predict_example.py
```

Пример загрузит модель, посчитает признаки и покажет решения по операциям.
Обучение с нуля (нужен `synthetic/bank_transfers.csv` рядом с `pipeline/`):

```powershell
py pipeline/train_fraud.py
```

Около 20 секунд. Всё детерминировано (`SEED = 42`), повторный запуск даёт те же цифры.

## Что нужно бэкенду

Три шага, и только второй требует внимания:

```python
from features import add_features, feature_matrix
from policy import make_decision

scored = add_features(df)                          # 1. признаки
p = model.predict_proba(feature_matrix(scored))[:, 1]  # 2. вероятность
decision = make_decision(p, t_review, t_block)     # 3. решение
```

Готовые обёртки — в `predict_example.py`:

| Функция | Когда использовать |
|---|---|
| `score_dataframe(df, model, t_review, t_block)` | пачка операций, история уже в `df` |
| `score_new_operation(op, history, ...)` | одна новая операция на фоне истории |

### Контракт

**Вход** — таблица операций с колонками:

| Колонка | Тип | Смысл |
|---|---|---|
| `timestamp` | datetime | время операции |
| `sender_id` | строка | счёт отправителя |
| `sender_balance` | число | баланс до операции |
| `amount` | число | сумма перевода |
| `receiver_id` | строка | счёт получателя |

Строки должны быть **отсортированы по времени**. Признаки истории
(`payee_tx_before`, `amount_to_avg`, `is_new_payee`) смотрят на предыдущие
строки — при перемешанном порядке «прошлое» перестанет быть прошлым.

Для одной новой операции нужна история её отправителя и получателя: без неё
`is_new_payee` и `amount_to_avg` посчитать не из чего. В демо история — это CSV,
в проде — запросы к базе.

**Выход**:

| Поле | Смысл |
|---|---|
| `p_fraud` | вероятность фрода от 0 до 1 (откалибрована) |
| `decision` | `0` — пропустить, `1` — проверить, `2` — заблокировать |

Пороги `0.14` / `0.46` лежат в `artifacts/thresholds.json`, а не в коде:
их можно менять без переобучения.

### 13 признаков

Порядок фиксирован — модель обучена именно на нём:

`hour, dow, night, amount, sender_balance, amount_ratio, is_new_payee,
payee_tx_before, days_since_first_payee, sender_tx_before, amount_to_avg,
receiver_tx_before, is_round`

Добавили признак — переобучите модель. Иначе `predict_proba` либо упадёт,
либо (хуже) молча посчитает не то.

### Если что-то пошло не так

- **Модель не загрузилась или файл повреждён** — не пропускать операцию молча.
  Сбой должен быть виден: лог, алерт, очередь на ручную проверку. Молчаливое
  «пропустить» — худший из вариантов, потому что выглядит как нормальная работа.
- **`p_fraud` равен `NaN`** — `score_dataframe` выбрасывает `ValueError`.
  Это защита: без неё `NaN` превратился бы в решение `2` (блокировка).
- **Пороги перепутаны** (`t_block <= t_review`) — `make_decision` выбрасывает
  `ValueError`, иначе зона проверки исчезла бы и всё улетало в блокировку.
- **Неизвестный получатель** — отдельной обработки не нужно: все признаки
  числовые, категориальных кодировщиков нет.

### Безопасность

`.joblib` — это pickle: при загрузке он восстанавливает Python-объекты и может
выполнить произвольный код. Загружайте только свои артефакты, не принимайте
файл модели от посторонних. Наружу модель не отдавать — только её ответы.

Если бэкенд не на Python, `.joblib` не подойдёт: нужен ONNX или отдельный
Python-сервис, который отдаёт `p_fraud` по HTTP.

### Производительность

`score_new_operation` пересчитывает признаки по всей истории — O(n) на запрос.
Для демо и небольших объёмов нормально. В проде счётчики (число переводов,
средняя сумма, дата первого контакта) держат в базе и обновляют инкрементально.

## Четыре идеи, на которых всё держится

**1. Признаки только из прошлого.** `add_features` использует `cumcount()` и
`transform("first")` по отсортированным данным — они смотрят на предыдущие
строки. Если посчитать `value_counts()` по всему датафрейму, в признак попадёт
будущее, и метрики станут красивыми и ложными.

**2. Сплит по времени, а не случайный.** Клиенты повторяются (600 человек на
9 тыс. операций). При случайном сплите один и тот же отправитель попадает и в
train, и в test — модель его «узнаёт» и показывает завышенное качество.

**3. Калибровка.** `class_weight="balanced"` нужен, чтобы модель не игнорировала
1% фрода, но он искажает вероятности. `CalibratedClassifierCV(method="sigmoid")`
возвращает их к реальной шкале: `0.8` снова означает «примерно 80%».

**4. Пороги — из денег, а не из головы.** `choose_thresholds` перебирает пары
порогов и считает суммарные потери: проверка 50 ₽, ложная блокировка 500 ₽,
пропущенный фрод — сумма операции, при проверке оператор ловит 90% ущерба.
Побеждает самая дешёвая комбинация.

## Как менять под себя

- **Стоимости** — словарь `COSTS` в начале `train_fraud.py`.
- **Дата сплита** — `TEST_START = pd.Timestamp("2025-03-01")`.
- **Новый признак** — расчёт в `features.add_features`, строка в `FEATURES`,
  описание в `FEATURE_DESCRIPTIONS`, затем переобучение. Отчёт подхватит сам.
- **Пороги без переобучения** — править `artifacts/thresholds.json`
  (или пересчитать через `choose_thresholds`).

## Если что-то сломалось

- `ValueError: Слишком мало фрода` — сдвиньте `TEST_START` или перегенерируйте данные.
- `KeyError` / `ValueError: нет колонок` — в CSV не хватает полей из контракта.
- `TypeError: timestamp должен быть datetime` — дата не распарсилась при чтении.
- `InconsistentVersionWarning` — версии пакетов отличаются от `requirements.txt`.
- Кириллица в консоли превращается в кракозябры — запускайте с
  `$env:PYTHONIOENCODING='utf-8'` (в PowerShell) или используйте Windows Terminal.
